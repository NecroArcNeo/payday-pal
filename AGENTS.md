## Architecture rules
- Local-first: the app runs with no account. Data lives in an on-device Postgres (PGlite, IndexedDB `meridian-payroll`) opened by the `_authenticated` (ssr:false) layout, which no longer requires sign-in. Only one tab may open it (Web Lock); a second tab shows a blocker.
- Desktop app (Electron, `electron/`): `npm run dist:win` builds the static pages (`vite build --mode desktop`, TanStack Start SPA mode, no Node server) and a per-user NSIS installer in `release/`. The main process (`electron/main.mjs`) serves `dist/client` at `app://meridian/` and runs the payroll database itself, with PGlite on a real folder (`%APPDATA%\Meridian Payroll\database`, deliberately not Documents, which OneDrive may sync mid-write). Automatic backups are JSON files in `Documents\Meridian Payroll\Backups`, written to a temp file, fsynced and renamed. The page reaches both only through `window.meridianDesktop` (`electron/preload.cjs`, typed in `src/lib/desktop.ts`); `localDb()` and `backups.ts` switch to it when present, so pages and the store don't know which they're on. Transactions cross the bridge as begin/query/end and are rolled back if the page reloads or closes. Only one copy of the app runs (single-instance lock). Google sign-in is hidden in the desktop app (its redirect can't reach `app://`). `MERIDIAN_HOME=<folder>` moves the database and backups for testing.
- Pages read and write only through `src/lib/db` (`useEmployees` etc. in `src/lib/payroll.ts` for reads, `db().insert/update/remove/...` for writes). `db()` is the local store, or the Supabase store when the user picked "Edit cloud directly". Never call `supabase.from(...)` from a page.
- The local schema (`src/lib/db/schema.ts`) mirrors the cloud tables minus `owner_id`. Changing a table means: a new cloud migration, a new appended entry in `LOCAL_MIGRATIONS`, and bumping `SCHEMA_VERSION` in both `schema.ts` and the cloud sync functions.
- Sync is whole-database: push replaces the account's cloud copy, pull replaces this device's copy. Both refuse to overwrite changes from elsewhere without confirmation, and both save a verified backup of whatever they replace (local backups in IndexedDB `meridian-payroll-backups`; cloud backups in `cloud_backups`). Keep it that way: no code path may delete or replace payroll data without a backup first.
- Private fields (`src/lib/db/privacy.ts`, chosen per device on Sync & backup, stored in local `_meta`) never reach the cloud: push sends `redactSnapshot`, pull and cloud-backup restores apply `keepPrivate` (this device's values win), and `cloudStore` strips them from employee writes. Default: ID numbers (`sensitive` fields). Employee ID, names and hourly rate always sync. Any new path that sends employee data to the cloud must strip them too.
- Cloud: every table has `owner_id` (default `auth.uid()`), RLS is owner-only, and keys are `(owner_id, id)`. `push_snapshot` / `pull_snapshot` / `sync_status` (drizzle/migrations/0003) are the sync API; `sync_meta.version` is bumped by triggers on any cloud write.
- Worked hours for clock entries are computed by a DB trigger (`compute_record_hours`) in both the local and cloud databases, so imports and manual entries share one formula.
- File imports are parsed client-side with SheetJS (`xlsx`). The user maps each column to a field and picks the header row and row range per sheet; parsing lives in `src/lib/import/parse.ts` (pure, tested). Excel dates/times are read from cell serials, never from display text. Imports back up first and skip shifts already saved (`recordKey`).
- Theme is a `.dark` class on <html>, set pre-hydration by an inline head script from localStorage.
- Custom employee categories live in employee_field_defs; values in employees.custom_fields keyed by def id (so renames keep data). A def's `field_type` (src/lib/field-types.ts: text, long text, number, money, date, time, yes/no, email, phone, link) picks its input (`CategoryInput`) and display (`CategoryValue`); values stay strings, and ones that don't fit their type are kept and flagged, never dropped. Pay is computed client-side in `src/lib/pay.ts` (`employeePay`): Saturday/Sunday hours are always overtime (setting `weekend_overtime`), Mon–Fri hours past `ot_threshold` in a Mon–Sun week are overtime, each day's shift multiplier (`time_records.shift_id` when set, else `employees.shift_id`, null = first shift) scales the rate for regular hours only — overtime is rate × `ot_multiplier`, never stacked with the shift — `time_records.pay_override` pays a day exactly that amount, and `employees.pay_type = 'salary'` pays `ot_threshold` hours × rate × shift for each week with records (no overtime), shared across the week's days by hours. Per-record pay (`recordPay`/`payByRecord`, `useRecordPay` in tables) uses the same rules over whole weeks. Payroll loads whole weeks around the period (uncapped) so weekly overtime is right.
- Employee lookups everywhere use `searchEmployees`/`matchesEmployee` (src/lib/employee-search.ts) via `SearchInput` and `EmployeePicker` (src/components/EmployeeSearch.tsx), which take an `EmployeeFilter` (text plus exact department/position dropdowns); use those instead of plain <select>s. Bulk edits/deletes call `backupBefore(...)` first and use the store's `updateMany`/`removeMany`.
- The Time records list pages through the store (`listRecordsPage`, 50 at a time) with filters applied in the database; "Edit all"/"Delete all" act on every matching record via `listRecordsMatching`, not just the loaded page. Dates show their weekday via `weekday()`; use `isoDate()` (local calendar date) rather than `toISOString()` for "today".
- Tables use `<DataTable id=...>` (src/components/DataTable.tsx) instead of a bare <table>: column dividers, drag a cell's right/bottom edge to resize its column/row, double-click to reset. Cells don't wrap; every column is laid out at its widest entry (or a dragged width, if wider) whenever rows change, and only dragged widths are saved, so editing a row never leaves a column wide. Controls in table cells need explicit widths (a `w-full` input asks for the browser's default size) and `block` when stacked. Widths are keyed by the header's alias key when it has an `EditableLabel`. Column widths are remembered per table id via `src/lib/prefs.ts`, which also holds the other per-device display preferences (nav tab order, break unit). Field, category, section and column labels can be renamed by the user with aliases (`src/lib/labels.ts`, per-device pref): render a label with `<EditableLabel k=... name=...>` (or `useLabels().label` / `labelOf` where it can't be clicked, e.g. options and CSV headers), keyed by concept so one alias shows everywhere: employee column name, `custom:<def id>`, `section:<title>`, `extra:<category>`, or the shared column keys (`date`, `hours`, `reg_pay`…). Aliases never change stored names. Breaks are stored as minutes (`lunch_minutes`) and shown/typed in the user's unit via `src/lib/breaks.ts` and `BreakInput`.
