## Architecture rules
- The app is called KoPayroll (it was Meridian Payroll; that name belongs to an existing company, so never show it). Internal names that existing data depends on keep `meridian`: the `app://meridian` origin (localStorage and the templates' IndexedDB belong to it), `meridian-*` pref keys, `MERIDIAN_*` environment variables, `window.meridianDesktop`, the `meridian_*` SQL functions, the key-derivation labels and the backup file `format` strings. Changing any of them loses or locks existing data.
- Local-first, desktop only: the app runs with no account, in its Electron window (no browser version). Data lives in one SQLite file encrypted with SQLCipher (`better-sqlite3-multiple-ciphers`, N-API prebuilt binary: no compiling, the same binary in Node tests and Electron) in the main process, opened by the `_authenticated` (ssr:false) layout, which no longer requires sign-in; opened in a plain browser tab, that layout shows "KoPayroll runs in its desktop window" (`NotDesktopError`). `npm run dev` (`scripts/dev.mjs`) starts the Vite dev server (or reuses one on :8080) and opens the window on it (`MERIDIAN_DEV_URL`, hot reload) with its data in `.dev-data/` (git-ignored); `npm run dev:web` is the dev server alone. Vite's watcher ignores `.dev-data/` and `release/` (the window holds files there open, which crashed it).
- Desktop app (Electron, `electron/`): `npm run dist:win` builds the static pages (`vite build`: TanStack Start in SPA mode only; there is no web server, server functions or SSR, and `src/start.ts` is an empty `createStart` the route generator expects) and a per-user NSIS installer in `release/`. The main process (`electron/main.mjs`) serves `dist/client` at `app://meridian/` and runs the payroll database itself: `database/payroll.db` (plus SQLite's `-wal`/`-shm` while open) under `%APPDATA%\KoPayroll` (deliberately not Documents, which OneDrive may sync; the app was called Meridian Payroll before, and `appFolder` renames an old `%APPDATA%\Meridian Payroll` to it as a whole on the first start, or keeps using the old one if the rename fails), opened by `openDatabase` (`electron/database.mjs`: SQLCipher 4 with a raw key, WAL with `synchronous=FULL` so a reported save is on disk, foreign keys on, and the SQL functions `meridian_flag`/`meridian_set`/`meridian_bypass` standing in for Postgres' session settings; `endTransaction` clears the one-transaction flags) and checked with `PRAGMA quick_check` at every start (damage, or a page changed outside the app, fails its HMAC → `RecoveryScreen`). Queries use `$1`… parameters (`runQuery` binds them by number). Automatic backups are JSON files in `%APPDATA%\KoPayroll\Backups`, written to a temp file, fsynced and renamed; they hold private fields, so never put them anywhere that syncs. Backup files that leave the app go through `saveBackupFile`/`readBackupFile` (`src/lib/backup-file.ts`): password-encrypted by default (`src/lib/backup-crypto.ts`, AES-GCM + PBKDF2), unencrypted only if the user ticks it. The page reaches both only through `window.meridianDesktop` (`electron/preload.cjs`, typed in `src/lib/desktop.ts`; `bridgeDb` in local.ts). Transactions cross the bridge as begin/query/end (one at a time: other queries wait until it ends; `transactionGate` in database.mjs, shared with the tests, checks "none open" and runs in the same tick, since an await between would let a waiting query run inside the next transaction) and are rolled back if the page reloads or closes. Only one copy of the app runs (single-instance lock). Cloud sign-in is email and password only (an OAuth redirect can't reach `app://`). If the database can't be opened, the `_authenticated` layout shows `RecoveryScreen`: the user picks a backup (or a file), the main process moves the data folder aside to `database-damaged-<time>` (never deleted) and the backup is restored into a new one. `session.json` in the app folder records whether the database was closed cleanly; after an unclean end the next start reads every table before trusting it, and tells the user. A `database/` folder from before SQLite (Postgres' `PG_VERSION`) is moved to `database-pglite-<time>` (never deleted) and the user is told to restore a backup. Encryption on the device: SQLCipher's key is HKDF(data key, "meridian database"). The data key (random, never changes) is in `keyring.json` (userData), wrapped by Windows DPAPI via `safeStorage` (only while there is no app password), the app password (PBKDF2 600k), a recovery key (shown once, 32 base32 characters) and optionally a cloud escrow key (email reset: cloud migration 0016 `key_escrow`, reached through `set/get/delete_key_escrow`, unlocked with an emailed sign-in code, `src/lib/key-escrow.ts`); losing keyring.json loses the data, and a new key is never made over an existing `payroll.db`. `safeStorage`'s own key is in Chromium's `Local State` file, written seconds after first use, so the first keyring is saved only once that key is on disk (`windowsKeySaved`): a crash in that window would otherwise lock the data for good. Until unlocked, the main process refuses every `db:*` and `backups:*` call; `DataGate` asks `security.status()` first and shows `LockScreen` (password, recovery key, email code, or "start over": moves the database and keyring aside as `database-locked-*`/`keyring-*.json`, never deleting them). Wrong guesses slow down (doubling, up to 30 s). Changing the password, recovery key or email reset needs the current password and only rewraps the key. Automatic backups are sealed (AES-GCM, `seal`/`unseal` in `electron/keyring.mjs`) with their id/date/reason/counts readable for listing; old unsealed ones are sealed in place at start. The Security panel on Sync & backup (`SecurityPanel`) manages it. Not covered: Chromium's own storage (prefs, templates, the cloud sign-in token), exported files, and `database-damaged-*` folders. `MERIDIAN_HOME=<folder>` moves the database and backups for testing; with it set, `MERIDIAN_HIDDEN=1` never shows the window (automated tests running in the background; ignored without `MERIDIAN_HOME`, so the real app can't start invisible).
- Pages read and write only through `src/lib/db` (`useEmployees` etc. in `src/lib/payroll.ts` for reads, `db().insert/update/remove/...` for writes). `db()` is always this computer's database (`localStore`; there is no cloud editing mode), and the cloud is reached only by push/pull and cloud backups in `src/lib/db/sync.ts` (kept, with the Supabase client, email sign-in, `key-escrow.ts`, the cloud migrations and their PGlite tests, for cloud sync). Never call `supabase.from(...)` from a page.
- The local schema is SQLite (`src/lib/db/sqlite-schema.ts`: `SQLITE_SCHEMA` is schema 12 in one go for a new database, frozen at schema 12's tables and columns (`V12_TABLES`, `ADDED_LATER`), and every database, new ones too, then runs `SQLITE_MIGRATIONS`, where later changes are appended; a migration that adds columns to a table remakes its undo triggers (`remakeUndoTriggers`), since their row images list every column; `SCHEMA_VERSION` in schema.ts = `SQLITE_BASE_VERSION` + migrations, tested). Every column's kind is in `COLUMNS` (`src/lib/db/codec.ts`), which drives the DDL test, `encodeRow` (true → 1, objects → JSON text, "8:00" → "08:00:00", ISO timestamps, money rounded half away from zero on the decimal digits with `roundDecimal`) and `decodeRow` (back to the shapes the cloud and snapshots use); every read and write of a payroll table goes through it, so a new column goes in `COLUMNS`, the DDL and the snapshot `upgrade`. Date and time checks use `is`, not `=` (a CHECK that comes out NULL passes in SQLite). The triggers mirror the cloud's: worked hours (checked before the write, filled in after it, skipped while undo replays), change_seq, the paid-day locks (`RAISE(ABORT, …)` with the same messages), rate history (`date('now','localtime')`), the undo log (`json_object` of every column, generated from `COLUMNS`). The cloud is still Postgres (drizzle/migrations): changing a table there means a new cloud migration and bumping the schema version in the cloud sync functions too. Tests open an in-memory database the app's way (`memoryDb` in `src/test/sqlite-db.ts`); PGlite remains only as a dev dependency for the cloud-SQL tests.
- Sync is whole-database: push replaces the account's cloud copy, pull replaces this device's copy. Both refuse to overwrite changes from elsewhere without confirmation (naming the computer that pushed, from `sync_meta.pushed_by_*`, cloud migration 0010, and counting the rows that differ with `diffCounts`; each database has a `device_id`/`device_name` in `_meta`), and both save a verified backup of whatever they replace (local backups in the Backups folder; cloud backups in `cloud_backups`). Keep it that way: no code path may delete or replace payroll data without a backup first. Days up to `payroll_settings.locked_through` (schema 10) are locked as paid: database triggers (`refuse_locked`, `refuse_locked_rate`, local and cloud) refuse any write to time_records, pay_adjustments or pay_rates touching them, so every path obeys it; restores and pushes delete the settings first and insert them last, so they never meet their own lock. Locked days keep their pay (schema 12): locking saves each record's pay line in `time_records.frozen_pay` (`lockThrough`/`setRecordsLocked` in `src/lib/pay-freeze.ts` work it out with today's rules and pass it to the store's lock methods, which save it in the same transaction), `recordPay` uses it instead of the rules, shift multipliers and rates, and unlocking (moving the lock earlier, unlocking everything, or one record) clears it, so the current rules apply; undo puts it back. The triggers always allow changes to only `unlocked`/`frozen_pay`. Always lock through those helpers, never `setLockedThrough` without `freeze`. A single record can be unlocked by itself (`time_records.unlocked`, schema 11; `setRecordsUnlocked`): the triggers let unlocked records change, always allow switching the flag, and `setLockedThrough` clears every flag (moving the lock locks them again). `PayLock` (Payroll page, and Time records page) locks a period (only one that has ended: never days after today) or changes the lock and re-locks records unlocked one by one; locked rows show a lock that unlocks just that record when clicked, and the selection bar unlocks or re-locks selected records. Pay rate history entries are written one at a time (`writeRateHistory`): the lock lets the first change's "since the start" entry through only while it's the employee's only one. (Single-row deletes from a table's trash icon are the deliberate exception.) A migration that adds a table must also handle pre-update backups lacking it (`countRows`/`isEmpty` treat a missing table as empty; `upgrade` in snapshot.ts adds it). Automatic backups run every 30 minutes while data changed (`maybeAutoBackup`, checked by the `_authenticated` layout), when the desktop window closes, and before pending `LOCAL_MIGRATIONS` run (`migrate(db, backup)`, stamped with the old schema version, so keep `SCHEMA_VERSION` equal to `LOCAL_MIGRATIONS.length`). "Back up now" saves `manual` backups, which are never pruned; others thin out by age (`src/lib/db/retention.ts`). Copies on another drive (Sync & backup's "Copy backups to another drive", `BackupCopyPanel`): after every backup the main process also writes the newest into a folder the user picks (`electron/backup-copy.mjs`, settings in `backup-copy.json` in userData), not awaited, one at a time (`copyLatest`), so a slow or missing drive never holds up a save; quitting waits up to 20 s for one in progress (`before-quit`). Sealed backups need this computer's keyring, which a wiped disk takes too, so each copy is a backup file exactly as "Download backup file" makes it (`copyText`: the backup-crypto.ts format, PBKDF2 + AES-GCM, or plain if the user chose no password), opened by Restore from file anywhere; the key is derived from the password once and kept sealed with the data key (the password itself is never stored), and changing the password re-encrypts the copies already there (`rewriteCopies`). Each copy is read back and checked; named `KoPayroll backup - <computer> - <local time>.json` (`- saved by you` for manual ones, never pruned; copies named `Meridian backup - …` by the app's old name still count as this computer's), and only this computer's copies beyond "keep the newest" (5/10/30/100) are removed, never other files. A failed copy (an unplugged USB stick) is kept as `error`, shown on the panel, retried every 5 minutes, after the next backup and after unlocking; the folder is refused inside the app's own folder, and the user is warned when it's on the same drive or in a OneDrive/Dropbox folder. While copies work, the "download a backup file" reminder stays hidden. Once a day (2 minutes after opening, then on the 5-minute timer; `checkDue`), and on "Check now" on Sync & backup, the newest backup is restored into a scratch database to prove it restores (`checkNewestBackup`/`restoreCheck`, src/lib/db/backup-check.ts: the app's own `migrate` and `replaceWithSnapshot`, whose per-table count check fails on any missing row, then `integrity_check` and `foreign_key_check`); the scratch database is in memory in a worker thread (`electron/scratch-db.mjs` + `scratch-worker.mjs`, reached as `meridianDesktop.scratch`, same calls as `db`, only while unlocked; it starts per check and ends after, and falls back to the main thread only if a worker can't start). The result is a per-device pref (`BACKUP_CHECK`), shown under the backup list (`BackupCheckLine`); a failure is a toast that stays until dismissed.
- Private fields (`src/lib/db/privacy.ts`, chosen per device on Sync & backup, stored in local `_meta` as the list of fields that *do* sync, so new categories start private; default: only department, job title and hire date sync) never reach the cloud. Snapshots record them (`private_fields`) and restores keep the union of the device's and the backup's, so restoring never makes a field less private. The first push from a device lists what will upload and asks first (`privateFieldsConfirmed`). Push sends `redactSnapshot`, pull and cloud-backup restores apply `keepPrivate` (this device's values win). Employee ID, names and hourly rate always sync. Everything under Personal (date of birth, gender, nationality, passport, SSN, residential status: `sensitive` in employee-fields.ts, `PERSONAL_DETAILS`), and custom categories filed under Personal, stays on the profile: off timesheets and the payroll table, its column choices and exports. Any new path that sends employee data to the cloud must strip them too.
- Cloud: every table has `owner_id` (default `auth.uid()`), RLS is owner-only, and keys are `(owner_id, id)`. `push_snapshot` / `pull_snapshot` / `sync_status` (drizzle/migrations/0003) are the sync API; `sync_meta.version` is bumped by triggers on any cloud write.
- Worked hours for clock entries are computed by a DB trigger (`compute_record_hours`) in both the local and cloud databases, so imports and manual entries share one formula.
- File imports are parsed client-side with SheetJS (`xlsx`). The user maps each column to a field and picks the header row and row range per sheet; parsing lives in `src/lib/import/parse.ts` (pure, tested). Excel dates/times are read from cell serials, never from display text. Text dates never go through `new Date(text)` (it reads "Oct 5" as 2001 and "5" or "Week 3" as dates): year-less and month-name dates are read by `readTypedDate`, and an imported date with no year is the latest such day on or before today (a timesheet records work done; typed dates keep the nearest year, since upcoming shifts are typed too). Every typed or imported amount (day pay, bulk edit, money/number categories, imports) is read by `readAmount` (src/lib/amount.ts): "12,50" is 12.5, "1.234,56" is 1234.56, "(50)" is −50. Imports back up first and skip shifts already saved (`recordKey`). Pasted rows are a sheet like a file's (`readPasted`, src/lib/import/paste.ts, pure, tested: the clipboard's HTML table first (Excel, Google Sheets, Word, web pages), else the text split by tabs (spreadsheet quoting), commas, semicolons, pipes or runs of 2+ spaces, whichever gives steady columns; every cell stays text, so dates follow the import's date order), named `Pasted rows` (so its mapping is remembered like a sheet's): Ctrl+V on the Import or Time records page outside a text box, dialog or menu (`usePasteRows`), or the "Paste rows" button (`PasteRowsButton`, reads `navigator.clipboard`), in src/components/PasteRows.tsx; Time records hands the sheet over (`handOffPasted`/`takePasted`) and opens Import, which sets it up as hours. So a paste gets the whole import: mapping, header row, duplicate skipping, the backup, one undo step.
- Theme is a `.dark` class on <html>, set pre-hydration by an inline head script from localStorage. The app works offline: its fonts ship in `src/assets/fonts` (declared in `src/styles.css`), and nothing outside the cloud features may load from the internet (no CDNs, web fonts or remote images).
- Custom employee categories live in employee_field_defs; values in employees.custom_fields keyed by def id (so renames keep data). A def's `field_type` (src/lib/field-types.ts: text, long text, number, money, date, time, yes/no, email, phone, link) picks its input (`CategoryInput`) and display (`CategoryValue`); values stay strings, and ones that don't fit their type are kept and flagged, never dropped. Pay is computed client-side in `src/lib/pay.ts` (`employeePay`): Saturday/Sunday hours are always overtime (setting `weekend_overtime`), Mon–Fri hours past `ot_threshold` in a Mon–Sun week are overtime, each day's shift multiplier (`time_records.shift_id` when set, else `employees.shift_id`, null = first shift) scales the rate for regular hours only — overtime is rate × `ot_multiplier`, never stacked with the shift — each day is paid at the rate in force that day (`pay_rates`, schema 9: "from this date, this rate", read with `rateOn` in `src/lib/pay-rates.ts` and passed to pay as `rates`; a database trigger keeps the old rate whenever `employees.hourly_rate` changes, so no path can rewrite past pay, and `employees.hourly_rate` is always the latest entry's rate; the profile and bulk edit ask from which day via `askRateDate` and write the history first with `planRateChange`), `time_records.pay_override` pays a day exactly that amount, and `employees.pay_type = 'salary'` pays `ot_threshold` hours × rate × shift for each week with records (no overtime), shared across the week's days by hours; a manual day is paid its amount instead of its share (the other days keep only their own shares). Per-record pay (`recordPay`/`payByRecord`, `useRecordPay` in tables) uses the same rules over whole weeks. Payroll loads whole weeks around the period (uncapped) so weekly overtime is right.
- Employee lookups everywhere use `searchEmployees`/`matchesEmployee` (src/lib/employee-search.ts) via `SearchInput` and `EmployeePicker` (src/components/EmployeeSearch.tsx), which take an `EmployeeFilter` (text, where `-word` leaves people out, plus department/position `Facet`s: tick values to include any of them, or exclude some, via `FacetFilter` in src/components/FacetFilter.tsx); use those instead of plain <select>s. Other list filters with a fixed set of choices (e.g. the Time records shift filter) use `FacetFilter` too. Shifts can have usual hours (`shifts.default_clock_in/out/lunch_minutes`, schema 8, read through `src/lib/shift-times.ts`); the Time records form's "By shift" buttons select a shift's working people among those the employee search shows, and the form shows those hours, and when the picked shifts' hours differ, "Add each shift's usual hours" lists each shift with editable times (prefilled from its usual hours, or the form's when it has none) that each person gets for their record shift (or own shift). Under the times the form says which shift's usual hours filled them in, or that the shift has none, with "Set usual hours" (Settings → Pay rules). In the record side panel, choosing another person or shift fills in that shift's usual hours, with "Put back" for the record's own times (an hours record switched to clock starts from them too); in Patterns, choosing a shift for a day fills its hours, and when everyone on the pattern shares a shift with usual hours, one click uses them for every day on "their usual shift". Employee IDs are unique ignoring case (`employeeWithCode`, src/lib/employee-code.ts) wherever one is typed. Adding a record for someone who already has one that day asks first (`sameDayClashes`, src/lib/record-clash.ts, through `askChoice`/`ChoicePrompt`, an alert dialog with several answers and an optional date or text). Never use the browser's `confirm()`/`prompt()`/`alert()` (grey Windows boxes that freeze the page; Electron doesn't support `prompt()` at all): yes/no questions are `await askConfirm({ title, detail, items, confirm: "Delete 3 employees", danger })` (danger: red button, Cancel focused), a typed answer is `askText` (src/lib/choice-prompt.ts). Keyboard handlers that act on the page (side panels' Escape and ↑/↓, Ctrl+Z) skip while `modalOpen()` (a modal dialog, a question or a menu); a menu item that opens a question or dialog keeps its focus there with `onCloseAutoFocus={keepDialogFocus}`. Employees rows have a ⋯ menu and the same menu on right-click (`EmployeeMenu.tsx`: one list of actions drawn with DropdownMenu or ContextMenu parts); deleting people backs up first and, when any has records on days locked as paid (which the database refuses to delete), says so before asking and offers to mark them resigned instead. The Timesheet page's Export menu is the kit's DropdownMenu. Undo/redo (`src/lib/db/undo.ts`, local data only, this session only): `localStore` is wrapped by `undoableStore`, so every write is one step; while a step runs, the `log_undo` triggers (schema 11, local only) log each row before/after into `_undo_log`, which is read into memory and emptied. Undo/redo write the rows back in one transaction, only over rows still exactly as the step left them (else `StaleUndoError` and the history is cleared), with `meridian.replaying` set so `record_rate_change` stays out; the record and extra-pay locks apply as usual, the pay-rate lock doesn't (steps are undone newest first, so undo only returns to rates the same lock already had, and it writes a first change's "since the start" entry in an order the per-row rule can't follow). Deleting an employee takes their rate history even on locked days (their locked records still refuse it). An action making several writes wraps them in `undoable(label, fn)` (mode.ts) so they undo together; it's also all or nothing: when `fn` throws, `UndoHistory.record` undoes what it already wrote at once (so such actions throw on a failed write instead of returning after a toast, as the profile save and bulk employee edit do). `UndoButtons` (in `AppShell`'s header) handles Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y, except while typing in a field. Timesheet exports (`TimesheetExport` on the Timesheet page): a plain .xlsx (SheetJS) or .csv, or the user's own Excel template: `src/lib/export/xlsx-template.ts` splices values into the template's sheet XML as text (unzipped with `fflate`; SheetJS's free edition drops styles on write): only the filled cells' text changes, every other zip entry stays byte-identical, and workbook.xml only gains `fullCalcOnLoad` (calcChain is dropped only when a formula is overwritten; a shared-formula master is refused). Never re-serialize a template part through a DOM. Sheets are read by local name, so strict-namespace and prefixed files work; hidden and chart sheets are listed (`templateSheets`). Each cell keeps its style; dates/times become Excel serials only where the cell's number format shows one. The editor shows the sheets as tabs and draws the chosen sheet as Excel does (`renderSheet`, `src/lib/export/sheet-render.ts`: fills incl. theme colours and tints, fonts, borders, alignment, merges, widths, heights, hidden rows/columns; text from SheetJS), with placed values marked on top; "Preview with this timesheet" draws the filled export the same way. Templates (`TimesheetTemplate`: cell per single value, a column letter per day-by-day field, first row, rows available, one row per record or per day, and optionally a number of whole weeks, starting on a chosen weekday (counting back from the period's start; default Monday) or on the period's first day (`weekStartOf`), so every day gets a dated row even without records) live in their own IndexedDB database `meridian-timesheet-templates` (`src/lib/export/template-store.ts`: `useTemplates`/`saveTemplate`/`deleteTemplate`; ones older versions kept in localStorage move there on first read), not in the payroll database; the values come from `timesheetData` (`src/lib/export/timesheet-export.ts`; its rows' money columns are rounded with `centsAddingUp` (src/lib/amount.ts, largest remainder), so each column adds up to its total cell exactly; the Reports table rounds each row's series the same way, so they add up to its Total), built for one employee by `employeeTimesheet` (`employee-timesheet.ts`, the Timesheet page's own pay rules), and the file by `exportFile`. "Export several…" (`BulkExport`) makes one file per chosen person for a period (one download, or a zip via `fflate`), and saves the choice of people, output and "leave out people with no records" as routines (`useRoutines`, a per-device pref; dates are picked each run). Date presets live in `src/lib/periods.ts`. PDF exports (plain, or a template as PDF; `src/lib/export/pdf.ts`, jsPDF, loaded only when used): the sheet laid out by `renderSheet` (a filled template, or `plainSheet` for the plain table) is fitted to A4 width (`pdfLayout`: trimmed, portrait or landscape, page breaks never through a merge, the sheet's print area and print-gridlines setting honoured) and drawn per page on a canvas, embedded as an image (browser text, so any alphabet; not selectable; template pictures aren't drawn). A template's formulas are worked out again for its PDF (`recalculate`, `src/lib/export/formula.ts`: arithmetic, comparisons, common functions, dates; references to other sheets), since Excel isn't there to do it; anything it can't work out (an unknown function, a defined name, a circular reference) refuses the PDF, naming the cell, never showing the template's stale cached result. Routines store the output as "xlsx" | "csv" | "pdf" | template id (Excel) | "pdf:" + template id (`exportKindKey`/`exportKindFrom`). Every table sorts by any of its columns (Employees, Time records, Timesheet and its extra pay, Dashboard, Payroll and its extra pay, the Reports numbers; the backup lists by when or kind): a table lists its columns once as `SortColumns` (src/lib/table-sort.ts, pure, tested: each column's label, `kind` text/number/date and the value it sorts by; `sortTable` is stable, puts empty cells last either way round, reads "E2" before "E10"; text starts A to Z, numbers and dates biggest/newest first unless `desc` says otherwise; ties by the table's own `tie`), keyed like the header's EditableLabel so aliases name them, and wraps its header row in `<TableSort>`; each header is a `SortTh` (src/components/SortControl.tsx: the label, then a small sort button, since clicking the label renames it; click again to reverse) and `SortControl` above the table is "Sort by [any column]" plus a flip button; both share one per-device pref (`useTableSort`, checked with `validTableSort`, which also maps old keys like `pay` → `total_pay`). Record lists share their columns (`recordColumns` in src/lib/record-columns.ts, built with shift names, the rate that day and pay lines by `useRecordSortColumns` in RecordPay.tsx; ties newest first, `newestFirst`). The Time records list sorts in the database by date, employee or hours (`RecordFilter.sort`, `recordOrder` in store.ts, `STORE_SORTED`); by any other column it loads every matching record (working out pay only for the pay columns) and pages the sorted list itself. The Timesheet keeps week subtotals only when sorted by date. The Reports table's period columns sort in time order, and its whole-period line stays last; its CSV follows the order shown. Not sortable on purpose: the Import preview (the file's own rows, picked by row number) and the shift list (its first shift is the default). Time records can be edited like a spreadsheet ("Edit in cells", `GridModeToggle`, a per-device pref; `useRecordGrid` in src/components/RecordGrid.tsx; what can be typed and how it's read is src/lib/record-grid.ts, pure, tested: date, shift by name, clock in/out ("9", "5pm", "1730"), break in the user's unit, hours (hours records only), note): click a cell or move with the arrows, type to replace (the caret stays after the typed key) or Enter/F2/double-click to change it, Enter saves and moves down, Tab right, Escape cancels; each saved cell is one `update` (one undo step; a blur after a programmatic move doesn't save twice). Ctrl+C copies a cell, Ctrl+V pastes a block from the active cell (`planGridPaste`: down the rows shown, right across editable columns; locked rows, unreadable cells and cells past the edge are left out and counted), asked first, backed up, one `updateMany`. Rows locked as paid are read-only. In this mode a row click doesn't open the side panel (its button does) and drag-select starts only from tick boxes (`boxesOnly`); the table's box has `data-own-paste`, which `usePasteRows` leaves alone. Rows of the Employees and Time records tables are selected by tick box, by dragging (`useDragSelect`, src/components/DragSelect.tsx: press a tick box or any part of a row that isn't a link or button and drag; every row passed over takes the state the first row gets, on top of the selection before the drag (`rangeSelection`, src/lib/drag-select.ts, pure, tested); the page scrolls near the window's edges, and the table is held still if something above it changes size, like the selection bar appearing; the click that ends a drag is swallowed), or Shift+click for a range from the last row pressed; a press that stays in its row is an ordinary click. Rows need `data-<attr>` ids on their `<tr>`. - Tables use `<DataTable id=...>` (src/components/DataTable.tsx) instead of a bare <table>: column dividers, drag a cell's right/bottom edge to resize its column/row, double-click to reset. Cells don't wrap; every column is laid out at its widest entry (or a dragged width, if wider) whenever rows change, and only dragged widths are saved, so editing a row never leaves a column wide. Controls in table cells need explicit widths (a `w-full` input asks for the browser's default size) and `block` when stacked. Widths are keyed by the header's alias key when it has an `EditableLabel`. `stickyHeader` keeps a table's header row in view while the page scrolls past it (moved with a transform: the panel's horizontal scrolling rules out position: sticky); give that `<thead>` the `grid-head` class (opaque, tinted, bold), as the Time records table does.
