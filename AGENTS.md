## Architecture rules
- Local-first: the app runs with no account. Data lives in an on-device Postgres (PGlite, IndexedDB `meridian-payroll`) opened by the `_authenticated` (ssr:false) layout, which no longer requires sign-in. Only one tab may open it (Web Lock); a second tab shows a blocker.
- Desktop app (Electron, `electron/`): `npm run dist:win` builds the static pages (`vite build --mode desktop`, TanStack Start SPA mode, no Node server) and a per-user NSIS installer in `release/`. The main process (`electron/main.mjs`) serves `dist/client` at `app://meridian/` and runs the payroll database itself, with PGlite on a real folder (`%APPDATA%\Meridian Payroll\database`, deliberately not Documents, which OneDrive may sync). Automatic backups are JSON files in `%APPDATA%\Meridian Payroll\Backups`, written to a temp file, fsynced and renamed; they hold private fields, so never put them anywhere that syncs. Backup files that leave the app go through `saveBackupFile`/`readBackupFile` (`src/lib/backup-file.ts`): password-encrypted by default (`src/lib/backup-crypto.ts`, AES-GCM + PBKDF2), unencrypted only if the user ticks it. The page reaches both only through `window.meridianDesktop` (`electron/preload.cjs`, typed in `src/lib/desktop.ts`); `localDb()` and `backups.ts` switch to it when present, so pages and the store don't know which they're on. Transactions cross the bridge as begin/query/end and are rolled back if the page reloads or closes. Only one copy of the app runs (single-instance lock). Google sign-in is hidden in the desktop app (its redirect can't reach `app://`). If the database can't be opened, the `_authenticated` layout shows `RecoveryScreen`: the user picks a backup (or a file), the main process moves the data folder aside to `database-damaged-<time>` (never deleted) and the backup is restored into a new one. `session.json` in the app folder records whether the database was closed cleanly; after an unclean end the next start reads every table before trusting it, and tells the user. The database opens with `DurableNodeFS` and `DURABLE_START_PARAMS` (`electron/durable-fs.mjs`): PGlite starts Postgres with fsync off, and its file layer has no fsync (Emscripten's fdatasync is a stub too), so without these a power cut could lose commits or leave the database inconsistent; with them each commit is flushed (`wal_sync_method=fsync`), and a failed flush is an error. Keep both when touching how the database opens. `MERIDIAN_HOME=<folder>` moves the database and backups for testing.
- Pages read and write only through `src/lib/db` (`useEmployees` etc. in `src/lib/payroll.ts` for reads, `db().insert/update/remove/...` for writes). `db()` is the local store, or the Supabase store when the user picked "Edit cloud directly". Never call `supabase.from(...)` from a page.
- The local schema (`src/lib/db/schema.ts`) mirrors the cloud tables minus `owner_id`. Changing a table means: a new cloud migration, a new appended entry in `LOCAL_MIGRATIONS`, and bumping `SCHEMA_VERSION` in both `schema.ts` and the cloud sync functions.
- Sync is whole-database: push replaces the account's cloud copy, pull replaces this device's copy. Both refuse to overwrite changes from elsewhere without confirmation (naming the computer that pushed, from `sync_meta.pushed_by_*`, cloud migration 0010, and counting the rows that differ with `diffCounts`; each database has a `device_id`/`device_name` in `_meta`), and both save a verified backup of whatever they replace (local backups in IndexedDB `meridian-payroll-backups`; cloud backups in `cloud_backups`). Keep it that way: no code path may delete or replace payroll data without a backup first. Days up to `payroll_settings.locked_through` (schema 10) are locked as paid: database triggers (`refuse_locked`, `refuse_locked_rate`, local and cloud) refuse any write to time_records, pay_adjustments or pay_rates touching them, so every path obeys it; restores and pushes delete the settings first and insert them last, so they never meet their own lock. Locked days keep their pay (schema 12): locking saves each record's pay line in `time_records.frozen_pay` (`lockThrough`/`setRecordsLocked` in `src/lib/pay-freeze.ts` work it out with today's rules and pass it to the store's lock methods, which save it in the same transaction), `recordPay` uses it instead of the rules, shift multipliers and rates, and unlocking (moving the lock earlier, unlocking everything, or one record) clears it, so the current rules apply; undo puts it back. The triggers always allow changes to only `unlocked`/`frozen_pay`. Always lock through those helpers, never `setLockedThrough` without `freeze`. A single record can be unlocked by itself (`time_records.unlocked`, schema 11; `setRecordsUnlocked`): the triggers let unlocked records change, always allow switching the flag, and `setLockedThrough` clears every flag (moving the lock locks them again). `PayLock` (Payroll page, and Time records page) locks a period or changes the lock and re-locks records unlocked one by one; locked rows show a lock that unlocks just that record when clicked, and the selection bar unlocks or re-locks selected records. Pay rate history entries are written one at a time (`writeRateHistory`): the lock lets the first change's "since the start" entry through only while it's the employee's only one. (Single-row deletes from a table's trash icon are the deliberate exception.) A migration that adds a table must also handle pre-update backups lacking it (`countRows`/`isEmpty` treat a missing table as empty; `upgrade` in snapshot.ts adds it). Automatic backups run every 30 minutes while data changed (`maybeAutoBackup`, checked by the `_authenticated` layout), when the desktop window closes, and before pending `LOCAL_MIGRATIONS` run (`migrate(db, backup)`, stamped with the old schema version, so keep `SCHEMA_VERSION` equal to `LOCAL_MIGRATIONS.length`). "Back up now" saves `manual` backups, which are never pruned; others thin out by age (`src/lib/db/retention.ts`).
- Private fields (`src/lib/db/privacy.ts`, chosen per device on Sync & backup, stored in local `_meta` as the list of fields that *do* sync, so new categories start private; default: only department, job title and hire date sync) never reach the cloud. Snapshots record them (`private_fields`) and restores keep the union of the device's and the backup's, so restoring never makes a field less private. The first push from a device lists what will upload and asks first (`privateFieldsConfirmed`). Push sends `redactSnapshot`, pull and cloud-backup restores apply `keepPrivate` (this device's values win), and `cloudStore` strips them from employee writes. Employee ID, names and hourly rate always sync. Everything under Personal (date of birth, gender, nationality, passport, SSN, residential status: `sensitive` in employee-fields.ts, `PERSONAL_DETAILS`), and custom categories filed under Personal, stays on the profile: off timesheets and the payroll table, its column choices and exports. Any new path that sends employee data to the cloud must strip them too.
- Cloud: every table has `owner_id` (default `auth.uid()`), RLS is owner-only, and keys are `(owner_id, id)`. `push_snapshot` / `pull_snapshot` / `sync_status` (drizzle/migrations/0003) are the sync API; `sync_meta.version` is bumped by triggers on any cloud write.
- Worked hours for clock entries are computed by a DB trigger (`compute_record_hours`) in both the local and cloud databases, so imports and manual entries share one formula.
- File imports are parsed client-side with SheetJS (`xlsx`). The user maps each column to a field and picks the header row and row range per sheet; parsing lives in `src/lib/import/parse.ts` (pure, tested). Excel dates/times are read from cell serials, never from display text. Imports back up first and skip shifts already saved (`recordKey`).
- Theme is a `.dark` class on <html>, set pre-hydration by an inline head script from localStorage.
- Custom employee categories live in employee_field_defs; values in employees.custom_fields keyed by def id (so renames keep data). A def's `field_type` (src/lib/field-types.ts: text, long text, number, money, date, time, yes/no, email, phone, link) picks its input (`CategoryInput`) and display (`CategoryValue`); values stay strings, and ones that don't fit their type are kept and flagged, never dropped. Pay is computed client-side in `src/lib/pay.ts` (`employeePay`): Saturday/Sunday hours are always overtime (setting `weekend_overtime`), Mon–Fri hours past `ot_threshold` in a Mon–Sun week are overtime, each day's shift multiplier (`time_records.shift_id` when set, else `employees.shift_id`, null = first shift) scales the rate for regular hours only — overtime is rate × `ot_multiplier`, never stacked with the shift — each day is paid at the rate in force that day (`pay_rates`, schema 9: "from this date, this rate", read with `rateOn` in `src/lib/pay-rates.ts` and passed to pay as `rates`; a database trigger keeps the old rate whenever `employees.hourly_rate` changes, so no path can rewrite past pay, and `employees.hourly_rate` is always the latest entry's rate; the profile and bulk edit ask from which day via `askRateDate` and write the history first with `planRateChange`), `time_records.pay_override` pays a day exactly that amount, and `employees.pay_type = 'salary'` pays `ot_threshold` hours × rate × shift for each week with records (no overtime), shared across the week's days by hours. Per-record pay (`recordPay`/`payByRecord`, `useRecordPay` in tables) uses the same rules over whole weeks. Payroll loads whole weeks around the period (uncapped) so weekly overtime is right.
- Employee lookups everywhere use `searchEmployees`/`matchesEmployee` (src/lib/employee-search.ts) via `SearchInput` and `EmployeePicker` (src/components/EmployeeSearch.tsx), which take an `EmployeeFilter` (text, where `-word` leaves people out, plus department/position `Facet`s: tick values to include any of them, or exclude some, via `FacetFilter` in src/components/FacetFilter.tsx); use those instead of plain <select>s. Other list filters with a fixed set of choices (e.g. the Time records shift filter) use `FacetFilter` too. Shifts can have usual hours (`shifts.default_clock_in/out/lunch_minutes`, schema 8, read through `src/lib/shift-times.ts`); the Time records form's "By shift" buttons select a shift's working people among those the employee search shows, and the form shows those hours, and when the picked shifts' hours differ, "Add each shift's usual hours" lists each shift with editable times (prefilled from its usual hours, or the form's when it has none) that each person gets for their record shift (or own shift). Employee IDs are unique ignoring case (`employeeWithCode`, src/lib/employee-code.ts) wherever one is typed. Adding a record for someone who already has one that day asks first (`sameDayClashes`, src/lib/record-clash.ts, through `askChoice`/`ChoicePrompt`, a dialog with several answers and an optional date). Undo/redo (`src/lib/db/undo.ts`, local data only, this session only): `localStore` is wrapped by `undoableStore`, so every write is one step; while a step runs, the `log_undo` triggers (schema 11, local only) log each row before/after into `_undo_log`, which is read into memory and emptied. Undo/redo write the rows back in one transaction, only over rows still exactly as the step left them (else `StaleUndoError` and the history is cleared), with `meridian.replaying` set so `record_rate_change` stays out; lock triggers apply as usual. An action making several writes wraps them in `undoable(label, fn)` (mode.ts) so they undo together. `UndoButtons` (in `AppShell`'s header) handles Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y, except while typing in a field. Timesheet exports (`TimesheetExport` on the Timesheet page): a plain .xlsx (SheetJS) or .csv, or the user's own Excel template: `src/lib/export/xlsx-template.ts` splices values into the template's sheet XML as text (unzipped with `fflate`; SheetJS's free edition drops styles on write): only the filled cells' text changes, every other zip entry stays byte-identical, and workbook.xml only gains `fullCalcOnLoad` (calcChain is dropped only when a formula is overwritten; a shared-formula master is refused). Never re-serialize a template part through a DOM. Sheets are read by local name, so strict-namespace and prefixed files work; hidden and chart sheets are listed (`templateSheets`). Each cell keeps its style; dates/times become Excel serials only where the cell's number format shows one. The editor shows the sheets as tabs and draws the chosen sheet as Excel does (`renderSheet`, `src/lib/export/sheet-render.ts`: fills incl. theme colours and tints, fonts, borders, alignment, merges, widths, heights, hidden rows/columns; text from SheetJS), with placed values marked on top; "Preview with this timesheet" draws the filled export the same way. Templates (`TimesheetTemplate`: cell per single value, a column letter per day-by-day field, first row, rows available, one row per record or per day, and optionally a number of whole weeks, starting on a chosen weekday (counting back from the period's start; default Monday) or on the period's first day (`weekStartOf`), so every day gets a dated row even without records) live in their own IndexedDB database `meridian-timesheet-templates` (`src/lib/export/template-store.ts`: `useTemplates`/`saveTemplate`/`deleteTemplate`; ones older versions kept in localStorage move there on first read), not in the payroll database; the values come from `timesheetData` (`src/lib/export/timesheet-export.ts`), built for one employee by `employeeTimesheet` (`employee-timesheet.ts`, the Timesheet page's own pay rules), and the file by `exportFile`. "Export several…" (`BulkExport`) makes one file per chosen person for a period (one download, or a zip via `fflate`), and saves the choice of people, output and "leave out people with no records" as routines (`useRoutines`, a per-device pref; dates are picked each run). Date presets live in `src/lib/periods.ts`. PDF exports (plain, or a template as PDF; `src/lib/export/pdf.ts`, jsPDF, loaded only when used): the sheet laid out by `renderSheet` (a filled template, or `plainSheet` for the plain table) is fitted to A4 width (`pdfLayout`: trimmed, portrait or landscape, page breaks never through a merge, the sheet's print area and print-gridlines setting honoured) and drawn per page on a canvas, embedded as an image (browser text, so any alphabet; not selectable; template pictures aren't drawn). A template's formulas are worked out again for its PDF (`recalculate`, `src/lib/export/formula.ts`: arithmetic, comparisons, common functions, dates; references to other sheets), since Excel isn't there to do it; anything it can't work out (an unknown function, a defined name, a circular reference) refuses the PDF, naming the cell, never showing the template's stale cached result. Routines store the output as "xlsx" | "csv" | "pdf" | template id (Excel) | "pdf:" + template id (`exportKindKey`/`exportKindFrom`). The Time records list can show oldest first (`RecordFilter.order`). Bulk edits/deletes call `backupBefore(...)` first and use the store's `updateMany`/`removeMany`.
- The Time records list pages through the store (`listRecordsPage`, 50 at a time) with filters applied in the database (including by shift: a record's own `shift_id`, or its employee's usual shift when it has none, via `RecordFilter.shifts`; excluded shifts are passed as the shifts left); "Edit all"/"Delete all" act on every matching record via `listRecordsMatching`, not just the loaded page. Dates show their weekday via `weekday()`; use `isoDate()` (local calendar date) rather than `toISOString()` for "today".
- Tables use `<DataTable id=...>` (src/components/DataTable.tsx) instead of a bare <table>: column dividers, drag a cell's right/bottom edge to resize its column/row, double-click to reset. Cells don't wrap; every column is laid out at its widest entry (or a dragged width, if wider) whenever rows change, and only dragged widths are saved, so editing a row never leaves a column wide. Controls in table cells need explicit widths (a `w-full` input asks for the browser's default size) and `block` when stacked. Widths are keyed by the header's alias key when it has an `EditableLabel`. `stickyHeader` keeps a table's header row in view while the page scrolls past it (moved with a transform: the panel's horizontal scrolling rules out position: sticky); give that `<thead>` the `grid-head` class (opaque, tinted, bold), as the Time records table does. Column widths are remembered per table id via `src/lib/prefs.ts`, which also holds the other per-device display preferences (nav tab order, break unit). Field, category, section and column labels can be renamed by the user with aliases (`src/lib/labels.ts`, per-device pref): render a label with `<EditableLabel k=... name=...>` (or `useLabels().label` / `labelOf` where it can't be clicked, e.g. options and CSV headers), keyed by concept so one alias shows everywhere: employee column name, `custom:<def id>`, `section:<title>`, `extra:<category>`, or the shared column keys (`date`, `hours`, `reg_pay`…). Aliases never change stored names. Breaks are stored as minutes (`lunch_minutes`) and shown/typed in the user's unit via `src/lib/breaks.ts` and `BreakInput`.
